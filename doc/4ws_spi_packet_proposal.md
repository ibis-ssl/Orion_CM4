# 4WS MainとのSPI通信案（未確定・未実装）

この文書は、crane→Orion_CM4の**4WS専用制御モード**、CM4→`4WS_MainFW`のSPI通信、およびCM4側の拡張方針を定める**仮仕様**である。mode 5の送受信とSPI通信はまだ実装されていない。実装済みのmode 3・4とG474向けUART通信は[制御パケット](control_packet.md)を参照する。

`4WS_MainFW`で確認できるのは、CM4とSPIで通信する要求、4輪駆動・4輪操舵の機体であること、TIM6による機体制御入口が500 Hzであることまでである。SPI通信、制御演算、アクチュエーター出力は未実装。SPI1はマスター、SPI2はスレーブとして生成されているが、CM4と接続するインスタンス・配線・CSの担当と極性は未確定である。以下のフレーム長・周期・数値表現は実装の決定事項ではない。

## crane→CM4：4WS専用制御モード案

65バイトのUDP外枠（先頭`CHECK_COUNTER`＋64バイト指令）と、指令byte 0..23の共通フィールドを維持する。指令byte 23の`CONTROL_MODE`に**`FOUR_WHEEL_STEERING_TARGET_MODE = 5`を追加する案**とする。mode 5は4輪それぞれの駆動周速度・操舵角を直接指定する。番号は仮予約であり、crane側の正本、CM4、シミュレータ、Main側の実装を揃えるまでは送信しない。

| 指令本体のbyte | mode 5での意味（案） |
|---|---|
| 0..23 | mode 3・4と同じ共通フィールド。byte 22の`STOP_EMERGENCY`を適用し、byte 23を`5`とする |
| 24..25 | モジュール0の駆動周速度 [m/s]、2バイト |
| 26..27 | モジュール0の操舵角 [rad]、2バイト |
| 28..31 | モジュール1の駆動周速度、操舵角を各2バイト |
| 32..35 | モジュール2の駆動周速度、操舵角を各2バイト |
| 36..39 | モジュール3の駆動周速度、操舵角を各2バイト |
| 40..63 | mode 5では予約、0 |

2バイトの値は、既存の`convertFloatToTwoByte`と同じ符号化を候補とする。範囲を`R`、物理量を`x`として、`raw = uint16_t(32767 × (x / R) + 32767)`とし、上位バイト、下位バイトの順に格納する。復号は`x = (raw - 32767) × R / 32767`。駆動周速度は`R = 32.767 m/s`（約0.001 m/s刻み）、操舵角は`R = π rad`（約0.000096 rad刻み）とする。`0x7FFF`は0、`0xFFFF`は未使用値として受信時に拒否する。これらは符号化できる範囲であり、実際の速度上限と操舵可動域は別途定める。送信前に有限性と符号化範囲を検査し、範囲外の値を黙って飽和させない。

mode 5ではbyte 32..37もモジュール目標の一部であり、mode 4の`TARGET_GLOBAL_POS`や`TERMINAL_VELOCITY`として復号しない。mode 3・4のbyte 24..63の意味は変更しない。mode 5専用のシリアライザとデシリアライザをcrane側の正本とCM4側に追加し、モード別に分岐する必要がある。現在の汎用シリアライザはbyte 32..37へ位置関連値を書き、byte 38..63を常にゼロ化する保証もないため、番号だけの追加ではこの配置にならない。

輪の番号と配置、角度の原点・正方向、速度と角度の許容範囲は未定義である。`STOP_EMERGENCY`時はmode 5の目標より停止を優先する。mode 5をG474向けUARTへ転送してはならず、対応しないMain構成では受信時に拒否して安全停止する。

crane→CM4とCM4→Mainは別の契約とする。CM4はmode 5を4輪目標という意味で解釈し、SPI指令へ符号化する。UART用72バイトフレームをSPIへそのまま流さない。mode 3・4を4WS機体でどう扱うかは、機体速度への変換と位置・方位制御の担当が決まるまで未定義とする。未定義のモードを別のモードとして黙って実行しない。

## SPIフレーム案

**案:** CM4がSPIマスターとなり、1回のCSアサートで両方向に128バイトずつ転送する。一定長なら受信バッファとDMA長を固定でき、ヘッダの長さでpayloadの有効範囲を判定できる。500 Hzの機体制御入口に合わせて最大500回/秒を候補とするが、SPIの実送信周期・クロック・Mode・CS配線は回路確認後に決める。

| byte | 内容（案） |
|---|---|
| 0..3 | ASCII `O4WS` |
| 4 | プロトコル版数 `1` |
| 5 | メッセージ種別 |
| 6..7 | 送信側の連番 `uint16`、little endian |
| 8..9 | 有効payload長 `uint16`、little endian（0..112） |
| 10..11 | 予約、0 |
| 12..123 | payload、残りは0 |
| 124..127 | byte 0..123のCRC32C、little endian |

CRC32Cの計算案は反転形多項式`0x82F63B78`、初期値`0xFFFFFFFF`、最終XOR`0xFFFFFFFF`とする。paddingの0も計算対象に含める。

CM4→Mainの種別案は`0x01`能力照会（payload長0）、`0x02`制御指令。Main→CM4は`0x81`能力応答、`0x82`状態通知とする。未対応の版数・指令種別・能力は動作指令として採用しない。

能力応答payloadは8バイトを候補とする。byte 0は基板種別`1`（4WS）、byte 1はモジュール数`4`、byte 2..3は対応指令ビット（bit 0が機体速度、bit 1が4モジュール目標）、byte 4..7はFW build IDとする。整数はlittle endian。安全停止は必須指令とし能力ビットを設けない。

制御指令payloadの先頭4バイトは、byte 0を指令種別（`0`安全停止、`1`機体速度、`2`4モジュール目標）、byte 1を安全フラグ（bit 0が非常停止）、byte 2..3を予約0とする案である。機体速度ではbyte 4..9に`vx, vy, omega`を各2バイトで格納する。4モジュール目標ではbyte 4..19に4組の`wheel_speed, steering_angle`を各2バイトで格納する。値の符号化とバイト順は上記のmode 5と同じとし、`vx, vy, wheel_speed`の`R`は`32.767 m/s`、`omega`の`R`は`32.767 rad/s`、`steering_angle`の`R`は`π rad`とする。安全停止の有効payload長は4、機体速度は10、4モジュール目標は20バイトとする。輪の並びと角度の原点・正方向は未定義であり、決定前に種別`2`を実装しない。SPIの固定転送長128バイトは引き続き仮案であり、payloadの縮小とは独立に回路確認後に確定する。

crane→CM4の`CONTROL_MODE=5`は、SPI制御指令の種別`2`へ変換する。数値`5`と`2`は別の通信境界に属する識別子である。SPI種別`1`は機体速度指令を後で利用できるようにする候補で、対応する上位モードからの変換と制御分担が決まるまで送信しない。

状態通知payloadは24バイトを候補とする。byte 0..1は最後に**受理した**指令の連番、byte 2はMainの状態（`0`初期化中、`1`準備完了、`2`駆動中、`3`安全停止、`4`異常）、byte 3は異常要約、byte 4..19は4組の実測`wheel_speed, steering_angle`（各2バイト）、byte 20..23はMain起動後の経過ミリ秒（`uint32`、little endian）とする。2バイト値の符号化と並びは指令と揃える。異常要約のビット割当と詳細な状態項目はMain側の計測項目が決まってから定義する。

SPIは同時送受信でもMainの応答準備に時間が必要なため、受信した状態が同じトランザクションの指令を反映すると仮定しない。連番の対応付けを仕様化し、初回やCRC不正の応答を状態として採用しない。「受理した連番」はアクチュエーターが目標を達成したことを意味しない。

## 受信検査と停止

- CM4とMainの双方でmagic、版数、種別、payload長、予約値、CRC、未使用の2バイト値を検査する。送信前に数値の有限性と符号化範囲を検査する。指令種別ごとの機構上の許容範囲は機構と制御分担が決まってから定める。
- Main側で「有効な新規指令を受理した時刻」を監視し、通信断時には出力を安全側へ移す。タイムアウト値は未確定とし、CM4の受信監視だけに安全を依存させない。
- 起動直後、能力照会失敗、対応しない指令、SPI障害、非常停止時は駆動を有効にしない。連番は受理結果の対応付けに使い、通信断判定には受信時刻も使う。

## Orion_CM4側の拡張方針

| 方法 | 評価 |
|---|---|
| `CONTROL_MODE=5`を追加し、既存UARTブリッジへSPIの処理も直接追加 | 上位の外枠は共通にできるが、SPIの全二重転送・状態受信とUARTの送受信が1つの処理へ集中する。採用しない。 |
| `CONTROL_MODE=5`を追加し、意味を持つ内部指令・内部状態と通信バックエンドを分ける | 65バイトの上位外枠を維持しつつ、安全判定と制御則を共有でき、UARTとSPIのフレームを独立に変更できる。推奨。 |
| 4WS専用の上位パケットと制御プロセスを全て別実装にする | 4WS固有の容量を確保しやすいが、位置制御・通信断停止・上位指令解釈が重複する。現時点では採用しない。 |

採用候補を実装する際の境界は次のとおり。

1. 搭載Mainの種類を起動設定で明示する。UART/G474とSPI/4WSを受信データから推測して切り替えない。未対応・未応答の構成は起動失敗として扱う。
2. 65バイト入力をモード別に復号し、`4モジュール目標`など意味を持つ内部指令に変換する。上位指令の解釈、位置制御、安全停止判定を機体側通信から分離し、UARTとSPIのエンコード・転送はそれぞれのバックエンドに閉じ込める。
3. SPIは全二重の1つのバスを1つの処理主体が所有し、指令送信と状態受信を同じトランザクションで管理する。UART用の`ai_cmd_v2.out`と`robot_feedback.out`をSPIへそのまま複製しない。
4. 能力照会を通して使える指令種別を確定し、G474構成のmode 5と4WS構成の未対応モードを拒否する。4WSの状態をG474の128バイトfeedbackへ無理に詰めず、上位に公開する状態形式も別途決める。
5. `cm4/firmware`のMain A/B更新・CANゲートウェイ更新ツールはUARTのプロトコルを前提とする。4WS向けFW更新経路は独立して設計するまで使用しない。
6. 現行UART実装と`cm4_sim`の動作・テストを維持したまま、共通の指令・安全ロジックと機体別バックエンドを段階的に分離する。4WS向けには実機と同じ指令解釈を使うシミュレーション用バックエンドも設ける。

## 仕様確定に必要な事項

- 回路図でCM4とMain間のSPIインスタンス、master/slave、CSの駆動側・極性・起動時レベル、クロック・Mode・DMA可否を確定する。`4WS_MainFW`の生成設定だけでは判断しない。
- 4輪の並び、駆動・操舵の正方向、操舵角の原点・可動域、速度上限、ゼロ速度時の操舵保持を決める。
- CM4とMainのどちらが車輪目標を生成し、どちらが速度・操舵の閉ループを担当するかを決める。
- 方位制御の担当と、上位の極座標速度・目標方位から機体座標速度へ変換するための姿勢情報を決める。
- 実測値・異常・非常停止・接続断時の処理、通信周期と許容遅延、mode 5の送信条件を決める。
- 4WS MainとCANノードのFW更新・版数照会をSPIで扱うか、別の保守経路にするかを決める。

この案を変更するときは、`4WS_MainFW`側の仕様書と同じバイト列・単位・停止条件に揃え、両側のゴールデンベクタと通信断試験で確認する。
